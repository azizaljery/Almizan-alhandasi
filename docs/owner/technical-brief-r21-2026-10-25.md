أبشر. من الآن لن نكتفي بإخبار مطوّر الميزان الهندسي ما الأخطاء التي يجب إصلاحها؛ بل سنعطيه الحل الهندسي، والخوارزمية المناسبة، وطريقة التنفيذ، وأمثلة الشيفرة، ثم التكليف المطلوب منه والاختبارات التي تثبت نجاحه.

وبالنسبة للجولة 21، أقترح أن نعالج أصل المشكلة في المحرك الثالث المبني على القيود، مع الحفاظ على AZIZ وMizan Score.

أولًا: الحل التقني الذي أريده للميزان

1. Brief Compiler

تحويل كلام العميل إلى متطلبات معمارية منظمة

2. Constraint Graph + Feasibility Solver

بناء العلاقات، والتحقق من إمكانية تحقيق الشروط

3. Topology Generator + Geometry Solver

ابتكار تنظيمات متعددة ثم تحويلها إلى أبعاد ومخططات

4. Hard Constraint Validator

رفض أي مخالفة إلزامية قبل تصنيف المخطط

5. AZIZ + Mizan Score + Diversity Engine

تقييم الجودة، واكتشاف التكرار، وترتيب البدائل

6. Client Explanation Engine

عرض النتائج أو تفسير العجز بصدق ووضوح

الفكرة الجوهرية: لا نجعل الذكاء الاصطناعي يرسم أي شيء ثم نطلب من Mizan Score اكتشاف الأخطاء. بل نجعل القيود والعلاقات تقود عملية الرسم من بدايتها.

الحل 1 — منع تفسير فشل المحرك بأنه استحالة معمارية

هذه مشكلة H6 وH10 تحديدًا.

يجب أن يرجع المحرك إحدى ثلاث نتائج واضحة، بدل استخدام حالة فشل واحدة لجميع الأسباب.

مثال TypeScript — عقد نتائج التوليد

type GenerationResult =
  | {
      status: "SOLVED";
      alternatives: FloorPlan[];
      requestedCount: number;
      warnings: string[];
    }
  | {
      status: "PROVEN_INFEASIBLE";
      conflictingConstraintIds: string[];
      proofReference: string;
      suggestions: string[];
    }
  | {
      status: "SEARCH_INCOMPLETE";
      reason:
        | "TIME_LIMIT"
        | "SEARCH_EXHAUSTED_WITHOUT_PROOF"
        | "SOLVER_ERROR"
        | "UNSUPPORTED_CASE";
      diagnosticId: string;
      retryable: boolean;
    };
interface FloorPlan {
  id: string;
  rooms: Room[];
  doors: Door[];
  parking: ParkingStall[];
  geometry: unknown;
}

كيف يعمل؟

* SOLVED: عُثر على بديل أو أكثر صالح.
* PROVEN_INFEASIBLE: أثبت محلّل قيود مكتمل لهذه المسألة عدم وجود حل، مع حفظ دليل التعارض.
* SEARCH_INCOMPLETE: لم يُعثر على حل، لكن لا يوجد دليل على استحالة الطلب.

لا يجوز استخدام PROVEN_INFEASIBLE لمجرد انتهاء المهلة أو فشل محاولة توليد.

والأهم: مقارنة 541 م² المتاحة مع 265 م² مطلوبة لا تثبت وحدها إمكانية التوزيع؛ فهناك الارتدادات، والأبعاد، والمداخل، والعلاقات، وشكل الأرض. لكنها أيضًا لا تبرر اقتراح حذف غرف دون معرفة القيد الحقيقي.

الحل 2 — إصلاح حركة الضيوف قبل رسم المخطط

هذه المشكلة تكررت في H1 وH5 وC7.

أقترح تمثيل العلاقات المعمارية على هيئة رسم بياني Graph؛ الغرف عقد، والأبواب وصلات، وكل غرفة تنتمي إلى منطقة وظيفية.

مثال TypeScript — فحص المسار الداخلي للضيف

type Zone = "guest" | "family" | "service" | "neutral";
interface Room {
  id: string;
  type: string;
  zone: Zone;
  floor: number;
  x: number;
  y: number;
  width: number;
  height: number;
}
interface Door {
  from: string;
  to: string;
  kind: "interior" | "exterior";
}
function hasPrivateGuestRoute(
  rooms: Room[],
  doors: Door[],
  majlisId: string,
  targetIds: string[]
): boolean {
  const byId = new Map(rooms.map(r => [r.id, r]));
  const visited = new Set<string>();
  const queue = [majlisId];
  const targets = new Set(targetIds);
  while (queue.length > 0) {
    const current = queue.shift()!;
    if (visited.has(current)) continue;
    visited.add(current);
    if (targets.has(current)) return true;
    for (const door of doors) {
      if (door.kind !== "interior") continue;
      const next =
        door.from === current ? door.to :
        door.to === current ? door.from : null;
      if (!next || visited.has(next)) continue;
      const room = byId.get(next);
      if (!room || room.zone === "family") continue;
      queue.push(next);
    }
  }
  return false;
}

النتيجة: لا يُقبل البديل إذا كان الشرط الإلزامي يقتضي مسارًا داخليًا من مجلس الرجال إلى الطعام أو المطبخ، ولم يوجد هذا المسار دون عبور منطقة العائلة.

لكن ينبغي أن يكون هذا الفحص ضمن التوليد نفسه، لا مجرد اختبار نهائي. كما يجب فحص أن الأبواب موجودة هندسيًا على جدران مشتركة، وليست مجرد وصلات افتراضية في الرسم البياني.

الحل 3 — منع الإصلاح الذي يخلق مشكلة جديدة

في الجولة 20 ظهرت أمثلة مثل صغر الصالة بعد إصلاح المطبخ، وحذف دورة مياه العائلة، وتضرر الإضاءة بعد تحسين الخصوصية.

الحل هو التحقق الشامل بعد كل تعديل هندسي، مع الاحتفاظ بالمخطط السابق إذا فشل التعديل.

مثال TypeScript — تعديل آمن للمخطط

interface Violation {
  constraintId: string;
  severity: "HARD" | "SOFT";
  message: string;
}
type Validation = (plan: FloorPlan) => Violation[];
function applySafeEdit(
  original: FloorPlan,
  edit: (draft: FloorPlan) => void,
  validate: Validation
): {
  accepted: boolean;
  plan: FloorPlan;
  violations: Violation[];
} {
  const draft = structuredClone(original);
  edit(draft);
  const violations = validate(draft);
  const hardFailures = violations.filter(
    v => v.severity === "HARD"
  );
  if (hardFailures.length > 0) {
    return {
      accepted: false,
      plan: original,
      violations
    };
  }
  return {
    accepted: true,
    plan: draft,
    violations
  };
}

ويجب أن تشمل validate فعليًا: وجود الغرف المطلوبة، المقاسات، الأبواب، مسارات الحركة، الخصوصية، المواقف، الحدود والارتدادات، ومتطلبات الدورين.

ولا يكفي هذا الفحص وحده لإثبات الجودة؛ فالتعديلات التي تجتاز القيود الإلزامية قد تظل ضعيفة معماريًا، وهنا يأتي دور AZIZ وMizan Score والمراجع المستقل.

الحل 4 — زيادة البدائل دون تكرارها

في C10 يطلب العميل خمسة بدائل، ولا يحصل إلا على واحد.

لا أريد أن يعالج المطور ذلك بتدوير المخطط أو عكسه أو تغيير أبعاد بسيطة.

أقترح آلية من مرحلتين:

* Topology Search: إنشاء علاقات تنظيمية مختلفة فعلًا؛ مثل اختلاف موضع الضيافة، ومسارات الخدمة، وتوزيع مناطق العائلة، وعلاقة الفراغات المفتوحة بالكتل.
* Geometry Optimization: إيجاد أبعاد ومواقع صالحة لكل تنظيم، مع رفض ما لا يحقق القيود.

ثم تُقارن البدائل عبر بصمتها المعمارية، مع اعتبار الدوران والانعكاس المكاني والتنقلات البسيطة صورًا مكررة عندما تبقى العلاقات الوظيفية نفسها.

مثال TypeScript — انتقاء البدائل المتنوعة

interface Candidate {
  plan: FloorPlan;
  hardViolations: Violation[];
  qualityScore: number;
}
function selectDiversePlans(
  candidates: Candidate[],
  requestedCount: number,
  architecturalDistance:
    (a: FloorPlan, b: FloorPlan) => number,
  minimumDistance: number
): FloorPlan[] {
  const valid = candidates
    .filter(c => c.hardViolations.length === 0)
    .sort((a, b) => b.qualityScore - a.qualityScore);
  const selected: FloorPlan[] = [];
  for (const candidate of valid) {
    const isDifferent = selected.every(existing =>
      architecturalDistance(
        existing,
        candidate.plan
      ) >= minimumDistance
    );
    if (isDifferent) {
      selected.push(candidate.plan);
    }
    if (selected.length === requestedCount) break;
  }
  return selected;
}

الدالة architecturalDistance يجب أن تُنفذ وفق معيار الاختلاف المثبّت سابقًا: علاقات الغرف والأبواب، الحركة، المناطق الوظيفية، وعلاقات الضيف والعائلة والخدمة. ولا يجوز اختراع عتبة جديدة بعد الاطلاع على نتائج الاختبارات المختومة.

الحل 5 — مواقف السيارات والحمامات متعددة الأدوار

هنا أريد تحسينًا في نمذجة الهندسة نفسها:

المشكلة	الحل البرمجي والهندسي
موقف غير قابل للاستخدام	فحص مساحة الوقوف، مسار الدخول والخروج، دوران المركبة، العوائق والأبواب
حمامات علوية غير منسقة	مطابقة مواقع المناطق الرطبة عبر إسقاط إحداثيات الأدوار، مع احتساب مسارات الخدمات
نافذة مجلس تكشف حوش العائلة	فحص خطوط الرؤية من نقاط مشاهدة محددة، وليس اتجاه النافذة فقط
الماستر في الواجهة	تحويل موقعها إلى قيد إلزامي فقط إذا اشترطه العميل، وإلا إلى تفضيل خصوصية
صالة أصغر من المجلس	مقارنة المساحات عند وجود شرط صريح أو معيار تصميمي معتمد، دون فرضه على كل مشروع

بالنسبة للمواقف، لا يكفي رسم مستطيل بمقاس سيارة؛ يجب إثبات إمكانية الوصول إليه ضمن هندسة الأرض. أما فحص الدوران فيمكن البدء بنموذج هندسي محافظ، ثم تطويره إلى محاكاة مسار المركبة.

ثانيًا: التكليف التنفيذي الجاهز للمطور

هذه الرسالة هي ما أقترح إرساله له. أمثلة الشيفرة أعلاه نماذج مرجعية وليست تعديلات مختبرة على مستودع الميزان؛ لذلك يجب تكييفها مع العقود والمكتبات الحالية، وعدم إنشاء محركات موازية بلا حاجة.

التكليف التقني للجولة 21 — الميزان الهندسي

أريد تنفيذ حلول تقنية فعلية للأسباب الجذرية التي كشفتها الجولة 20، وليس الاكتفاء بوصف الأخطاء أو إصلاح حالات بعينها.

اعتمد المبادئ والأمثلة البرمجية التي أرسلتها لك بوصفها تصميمًا مرجعيًا، ثم طبّقها بما يتوافق مع بنية المستودع الحالية وعقود AZIZ وMizan Score.

المرحلة الأولى — تشخيص البنية الحالية

افحص شيفرة المحرك الثالث المبني على القيود، وحدد:

1. أين تتحول متطلبات العميل إلى قيود؟
2. كيف تُنشأ العلاقات بين الغرف؟
3. كيف ينتقل المحرك من العلاقات إلى الإحداثيات والأبعاد؟
4. لماذا تفشل H4 وH6 وH10؟
5. كيف يميز المحرك بين التعارض الحقيقي وفشل البحث؟
6. أين تُحسب جودة المخطط وتنوع البدائل؟
7. كيف تُنشأ الرسائل التي تظهر للعميل؟

أريد تحديد السبب الجذري لكل فشل مع مسار الشيفرة المسؤول عنه، لا مجرد وصف النتيجة.

المرحلة الثانية — تنفيذ الحلول

أ. نتائج التوليد

نفّذ عقدًا واضحًا يفصل بين SOLVED وPROVEN_INFEASIBLE وSEARCH_INCOMPLETE.

لا تصنف الطلب مستحيلًا دون دليل صالح من محلل القيود. واحتفظ بسبب انتهاء البحث أو فشله.

ب. العلاقات المعمارية

نفّذ فحصًا بيانيًا لاتصال الغرف ومسارات الحركة، مع منع مرور الضيوف في منطقة العائلة عندما يكون ذلك شرطًا إلزاميًا.

اجعل العلاقات جزءًا من توليد المخطط قبل تثبيت هندسته.

ج. التعديل الآمن

نفّذ تحققًا شاملًا بعد كل تعديل هندسي، مع التراجع عن التعديل الذي يخرق شرطًا إلزاميًا.

امنع اختفاء غرفة مطلوبة أو فساد مسار حركة أو انتهاك مقاس أثناء إصلاح عيب آخر.

د. التنوع

طوّر البحث في التنظيمات المعمارية أولًا، ثم حل الهندسة لكل تنظيم.

طبّق مقياس الاختلاف المعماري المعتمد، واستبعد التكرارات والانعكاسات الشكلية التي لا تغير العلاقات الوظيفية.

هـ. الهندسة متعددة الأدوار والمواقف

نفّذ فحوصًا هندسية للمواقف ومسارات المركبات، ولتنسيق الخدمات والحمامات بين الأدوار، ولخصوصية النوافذ وخطوط الرؤية.

ميّز بين الشروط الإلزامية والتفضيلات والملاحظات التي تتطلب مراجعة مختص.

و. واجهة العميل

إذا تعذر العثور على مخطط، أظهر السبب الحقيقي بلغة مفهومة.

إذا كان العجز من المحرك، فاعترف بذلك صراحةً.

إذا طلب العميل خمسة بدائل ولم يتوفر سوى اثنين، أظهر العدد الحقيقي وأسباب عدم اكتماله.

امنع ظهور المصطلحات الداخلية والأرقام المتناقضة في أي رسالة للعميل.

المرحلة الثالثة — الاختبارات

نفّذ اختبارات وحدات وتكامل ومتصفح لكل حل.

أريد اختبارات تؤكد على الأقل:

* عدم تصنيف انتهاء المهلة على أنه استحالة.
* وجود مسار ضيافة داخلي صحيح دون اختراق الخصوصية.
* عدم حذف الغرف الإلزامية عند التعديل.
* مطابقة المقاسات المطلوبة طولًا وعرضًا.
* عدم قبول موقف لا يمكن الوصول إليه.
* كشف البدائل المكررة أو المعكوسة وظيفيًا.
* عدم تقديم أرقام أو أسباب متناقضة للعميل.
* عدم اعتماد أي مخطط يخالف شرطًا إلزاميًا.
* عدم اعتبار إصلاح حالة معروفة دليلًا على نجاح التعميم.

اختبر التغطية على مجموعة واسعة قابلة للإعادة، وسجّل نسبة الحلول الصحيحة، والتعارضات المثبتة، وحالات البحث غير المكتمل، وزمن التوليد، وعدد التنظيمات الجديدة المقبولة.

المرحلة الرابعة — التحقق المستقل

استخدم الحالات المعروفة لتطوير المحرك.

أبقِ H11–H15 محجوبة حتى اكتمال التطوير وتجميد إصدار المحرك ومعايير التقييم.

بعد التجميد، شغّلها مرة واحدة وفق البروتوكول المعتمد، ثم نفّذ المراجعة العمياء دون تعديل نتائجها.

لا تعتبر حالة التعارض المتعمد نجاحًا إلا إذا حدد المحرك التعارض الحقيقي وقدم تفسيرًا صحيحًا له.

المرحلة الخامسة — التسليم

أريد منك تسليم:

1. تقرير الأسباب الجذرية.
2. مخطط البنية البرمجية قبل التعديل وبعده.
3. الشيفرة المعدلة وأسماء الملفات ووظائفها.
4. شرح الخوارزميات والمعادلات والقيود.
5. نتائج اختبارات الوحدات والتكامل والمتصفح.
6. مقارنة حالات الجولة 20 بالجولة 21.
7. تقرير الاختبارات المختومة H11–H15 منفصلًا.
8. صور المساقط والمجسمات، بما فيها الحالات الفاشلة.
9. عدد البدائل الجديدة الصحيحة لكل حالة.
10. قائمة جميع العيوب المتبقية والقيود غير المدعومة.

لا تحذف AZIZ أو Mizan Score أو تستبدلهما دون إثبات الحاجة ومقارنة البديل، ولا تنشئ منظومة موازية إذا كان تطوير المنظومة القائمة ممكنًا.

لك صلاحية البحث والتطوير وإعادة الهيكلة داخل فرع التطوير المعزول، مع حفظ النسخ السابقة وإمكانية الاستعادة.

ممنوع النشر على الموقع الحالي أو الدمج في فرعي الإنتاج دون موافقتي الصريحة على إصدار محدد.

تبقى مراجعة معماري سعودي مرخّص شرطًا مستقلًا قبل طلب اعتماد النشر.

معيار النجاح

لن أعتمد الجولة لأن الاختبارات البرمجية نجحت فقط.

أريد إثبات أن المحرك أصبح:

* يفهم المتطلبات الجديدة.
* يجد تنظيمات معمارية مختلفة.
* يحولها إلى مخططات صحيحة.
* يحافظ على جميع القيود الإلزامية.
* يعترف بحدود قدرته بصدق.
* يحقق تحسنًا على الحالات الجديدة غير المستخدمة في التطوير.

نفّذ الحلول، ثم قدم أدلة نجاحها، ثم اعرض عليّ النتائج لاتخاذ القرار.

ثالثًا: كيف سنعمل في الجولات القادمة؟

أقترح أن يكون أسلوبنا ثابتًا:

المشكلة ← السبب الجذري ← الخوارزمية ← مثال الشيفرة ← مكان دمجها ← الاختبارات ← أمر التنفيذ للمطور.

وهناك نقطة مهمة: إذا أتاح المطوّر ملفات المحرك الحالي وعقود AZIZ وMizan Score، نستطيع الانتقال من أمثلة TypeScript المرجعية إلى تعديلات محددة على الملفات والدوال الفعلية بدل ترك مهمة التكييف كلها له.

أهم قرار تقني الآن: لا أريد استبدال المحرك الثالث فورًا بمحرك رابع. أريد أولًا إثبات أين يفشل المحرك الثالث، ثم إصلاح طبقات العلاقات والبحث والهندسة والتقييم بصورة قابلة للقياس. وإذا أثبتت الاختبارات أن بنيته لا تتحمل التطوير، عندها يكون استبدال الجزء المعطوب قرارًا هندسيًا مبنيًا على أدلة.
